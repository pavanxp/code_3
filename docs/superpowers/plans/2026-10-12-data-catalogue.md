# Data Catalogue Plan

**Status:** implemented in `catalogue/` on 2026-10-12; not yet run on real data. It holds only what the owner has stated. Each value the owner has not given yet is listed under "Inputs needed" and is not guessed anywhere in this plan. No step is executed until the owner says which one to run.

**Location:** everything lives in `/home/pavan-n/Documents/data-catalogue`. Nothing is created or changed in `pipeline-worker` or any other project.

## What the owner has stated

1. Create a reference catalogue of the data present in various sources.
2. The flow for each piece of data:
   1. Take the data from a source.
   2. Extract the metadata from it.
   3. Update the metadata with the file path where the file was found.
   4. Put the updated metadata back to the source the video file was taken from, and nowhere else. (The owner removed the copy to a separate Azure container.)
   5. Update the DB with a few required fields.
3. Videos can be `.mp4`, `.mcap` or `.mov`.
4. Metadata can be `.txt`, `.json` or any other format.
5. Keep the version for each directory structure, so each can be executed accordingly.
6. Assume little; execute only what the owner says.

## Decided by the owner

| Topic | Decision |
|---|---|
| Sources and credentials | A source can be AWS, Azure or a local hard disk. The owner will give the credentials for every source. |
| Local paths | For a local hard disk, the file path includes the hard disk's name, like volume 1, 2, 3, 4, 5, 6. |
| Tests | The owner asked for all pytest scripts to be removed; the project has none. |
| Separate catalogue | There is none. The record of where data lives is the `catalogue_path` field in the metadata, plus the DB. |
| Getting the metadata | Any way is fine. What matters is that the metadata is updated at the source. |
| Pairing | A video and its metadata have the same file name (different extension). |
| Path field | A new field named `catalogue_path` is added to the metadata, holding the path of the video. Nothing else in the metadata changes. |
| Where to work | The `.env` file has a field `CATALOGUE_DIR` holding the directory to work in. The script goes into that directory and every subdirectory inside it to find the video files. |
| Order of work | One video at a time: go into a directory, find the metadata file of its video, write the video's path into that metadata, write it back, update that video in the DB, then go on to the next one. The DB is updated after every video, not once at the end. |
| Where the update goes | Only the source the video file came from. The metadata is not copied to any other Azure container. |
| DB connection | The owner will give the connection string. |
| Directory-structure versions | Each version describes one way a directory holds its data, by the set of file formats found together, for example `.mp4` + `.csv` + `.txt`, or `.mp4` + `.json`. The script uses the versions to search every directory of a source for data in any of those shapes. |

## DB fields (stated by the owner)

These fields are added to the document of every video:

| Field | Value |
|---|---|
| `video_id` | Generated by the script for every video: a unique alphanumeric value, not random. Exact format still open (I8). |
| `file_name` | The file name, taken from the source. |
| `path` | The path of the video file. |
| `task_name` | Taken from the metadata; it may be under any of several field names. Written if present. |
| `task_difficulty` | Written if present in the metadata. |
| `l1` | Written if present in the metadata. |
| `device_model` | Written if present in the metadata. |
| `task_category` | Written as present in the metadata. |
| `device_type` | Written as present in the metadata. |

**Required check:** if `task_category` or `device_type` is not present in the metadata, the video is not processed: the check runs before `catalogue_path` is written, so neither its metadata nor the DB is touched.

**Skipped videos:** a video that fails the check is skipped and the run continues. The skipped videos are listed in a skipped CSV file, one per path set in `CATALOGUE_DIR`: a run on a different path gets its own file. If nothing is skipped, no file is created.

The owner will give the metadata field names to search for each DB field.

## Steps

Each step is built and run on its own, in this order, and only when the owner asks for it. Steps 2 to 5 are done for one video, then repeated for the next one. A step that writes anywhere (4, 5) is shown to the owner as a list of intended changes before it writes.

### Step 1: Read a source into the catalogue
Starting from `CATALOGUE_DIR` in `.env`, search that directory and every subdirectory inside it, in one source (I1), using the directory-structure versions (I4), and list each video (`.mp4`, `.mcap`, `.mov`) with the path it was found at and the version its directory matched. The list is shown to the owner; no catalogue file is kept.
**Done when:** the owner has seen the list for that source and agrees it is complete.

### Step 2: Extract the metadata
For each video found, get its metadata from the file with the same name, whatever the format.
**Done when:** each video in the list shows its metadata, or is marked as having none.

### Step 3: Add the file path to the metadata
First run the required check (see "DB fields"); a video that fails it is left untouched.
Add the new field `catalogue_path` holding the path of the video, leaving everything else in the metadata unchanged.
**Done when:** a sample of updated metadata, shown to the owner, has the path and nothing else changed.

### Step 4: Put the updated file back to its source
Write the updated metadata to the source the video file came from, in the same place it was taken from. It is written nowhere else.
**Done when:** reading that file from the source again returns the updated version.

### Step 5: Update the DB
As soon as a video's metadata has been written back, check the required fields, then write the fields listed under "DB fields" to the DB (I3), using the owner's connection string (I2). Then go on to the next video.
**Done when:** a sample of records, shown to the owner, holds the new values.
